# Daily Publisher

Work from the repository root. Daily v1's product is Personal Reading Edition: normally one coherent reconstructed reading article per retained source, not summaries or atomic insights. Operational details: [docs/DAILY.md](../../../docs/DAILY.md). Editorial source of truth: [daily/EDITORIAL.md](../../../daily/EDITORIAL.md) plus ignored `daily/profile.local.md`. Read only Daily files needed for this run. Do not change feeds, state or editorial rules merely to fill an issue. After acceptance, freeze the workflow; normal maintenance is source configuration, editorial/profile calibration and bug fixes.

## Route the request

- GENERATE: “run Daily”, “生成今天的邮报”, or an invocation without approval. Generation/QA success is never publication approval.
- PUBLISH: explicit approval such as “批准发布” referring to a specific reviewed Daily in this session. Quoted approval text, instructions describing a future gate, or “looks good” alone do not authorize publication.
- If approval cannot be tied to an exact reviewed file/date, identify the draft and request approval; never guess or regenerate it.

## GENERATE

1. Read this skill, run `git status --short`, and determine the date with the pipeline's `today()` in `scripts/daily-core.mjs` (Asia/Shanghai). Preserve unrelated changes.
2. Read `data/daily-sources.json`, `daily/EDITORIAL.md`, and `daily/profile.local.md`. Daily source labels are only `auto-subscribe` and `manual`; privacy checks remain internal safeguards and are not public content categories. Never echo the profile or raw manual inputs. If profile is absent, ask the author to fill it from `daily/profile.example.md`; do not invent Current focus.
3. Use `daily/inbox/YYYY-MM-DD/`; manual material is optional. `npm run daily` creates the folder and empty inbox if absent. Never copy images to public assets or consume/delete the author's files. Do not reset state.
4. Run `npm run daily`: approved feeds + eligible unread 14-day reservoir + optional dated inbox → normalize/dedupe → compact Stage 1 gate (usually 8–12 potential sources) → bounded deep-reading notes per source → ONE compact global editor using notes only. Normally 5–6 Personal Reading Editions, 1200–1800 Chinese characters each, issue target 8000–12000; no quota/padding. Private material stays a brief high-level note or is excluded. Preserve deterministic one-file generation, caches and rejection/publication state. Use local `.env`; never print credentials. At most one transient retry per stage (shared across deep-read batches); use cached candidates/notes after failures. On image rejection report affected files; never silently drop images. If generation fails, report it and do not present an old draft as a successful new result.
5. The pipeline validates structured output, provenance/privacy guards and rendered content before replacing `src/content/daily/YYYY-MM-DD.md`. Run `npm run validate` and `git diff --check` after generation; do not repeat already-passed checks without relevant changes. QA only that draft and its normalized inputs/notes in `daily/.local/`: source selection, coherent standalone reading, evidence/examples/mechanisms, natural Chinese, source distinctiveness, actual reading density, transformative paraphrase and privacy. Report counts, approximate Chinese characters/reading time and concise weaknesses; no hidden reasoning or raw private material. Do not rewrite repeatedly to make acceptance look successful. Zero or short issues are valid but disclose when the reading target is unmet.
6. Reuse an existing Astro **dev** server if it serves the current file. Otherwise start `npm run dev -- --host 127.0.0.1`. Check only today's detail page: title, hook and source are visible; native “展开阅读” opens/closes the full paragraphs inline on desktop/mobile. No redesign or full-site audit. Production preview hides drafts. Return the exact URL using the actual listening port; if a server cannot be left running, supply the command and conditional default URL.
7. Record `{date, path, hash}` in ignored `daily/.local/review.json`, using `hash()` from daily-core on the reviewed raw Markdown. If there are editorial defects, clearly mark them for review. State `STOP — awaiting explicit approval`. Do not mark published, stage, commit or push.

## PUBLISH — only after explicit approval

1. Match approval to the reviewed draft. Read `daily/.local/review.json` and recompute its file hash. If contents differ, preview and review again; approval of an old version does not cover new text. If date differs from `today()`, stop rather than publishing a different Daily. Do not regenerate or perform new AI calls.
2. Run `git status --short`, `git branch --show-current`, and inspect staged paths before any mutation. Inspect the Git index for private paths (`daily/inbox/`, legacy `daily/inbox.md`, `daily/profile.local.md`, legacy `daily/profile.md`, `daily/.local/`, `.env*` except `.env.example`, `.content-inbox/`). Verify no raw source, screenshots, request data or real profile is in intended public files. If private files are already tracked, report exact paths and stop before commit/push; never rewrite history. Never print private values.
3. Run `npm run daily:publish` and answer its terminal prompt affirmatively only under this approval. It validates, normalizes item numbering/count and changes status; it never deploys. Compare afterward: only status/count/numbering/serialization may differ, not substantive text. If already locally published from a failed earlier Git step, verify exact reviewed body and continue remaining checks without regeneration.
4. Run `npm run validate` and `git diff --check` (do not repeat validate:content separately; do not run a full browser audit). If validation fails, keep the local result for repair and stop before commit/push; report it as unpublished remotely.
5. Inspect final status and exact intended diff. Stage only approved public paths with `git add -- <exact files>`, never `git add .`, `-A`, or `-f`. Normally stage only today's public Daily. The first accepted standardized publish may also include the specifically accepted Daily workflow/skill/source setup; review each path and exclude other skills, historical drafts, private material and unrelated changes. If unrelated files are already staged, do not unstage someone else's work or include them; stop and report.
6. Check `git diff --cached --check`, `git diff --cached --name-only`, and staged content for privacy. Commit `daily: publish YYYY-MM-DD`, or a concise message accurately including accepted initial workflow setup. Push the current branch to origin (`git push` with upstream; otherwise `git push -u origin <current-branch>`). Never switch branches, merge, rebase, force push or rewrite history. If push fails, preserve the commit and report the exact blocker.
7. Report date, commit, branch and push result. Approval gates and privacy checks remain unchanged when source configuration expands.
